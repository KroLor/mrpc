# Упрощенный протокол RPC для ОС FreeRTOS

Проект поддерживает компиляцию под Windows с возможностью запуска программы как в режиме сервера, так и клиента для тестирования.
Для тестирования протокола на Windows используется асинхронный (`FILE_FLAG_OVERLAPPED`) и двунаправленный (`PIPE_ACCESS_DUPLEX`) канал Named Pipe, передающий поток байт.
Далее рассматривается интерфейс и реализация протокола, получившего название MRPC.

## Физический уровень

На этом уровне объявлен абстрактный класс `Physics`. Для каждой среды его реализация будет уникальной; например, для Windows это класс `PhysicsForWin`.
Интерфейс этого уровня, помимо прочих методов, обязан реализовывать методы `send`, `recv` и `update`.
* Методы `send` и `recv` отвечают за отправку и прием байтов (через указатель на начало данных и их длину) соответственно.
* Метод `update` обрабатывает состояния соединения и выполняет запись или чтение в специфичной для среды реализации через буферы с учетом роли устройства.

Таким образом, протокол не навязывает распределение ролей и конкретную реализацию физического уровня, но требует от него быстрой работы с данными через указатели, что обеспечивается использованием буферов. Класс `PhysicsForWin` как раз использует такой подход.

## Канальный уровень

Если на физическом уровне речь шла об уникальной реализации «клиент-серверной» части, то на канальном уровне используются методы физического уровня для побайтового получения данных и формирования пакетов/кадров (frame) канального уровня для передачи в физическую среду.
* Уровень использует два буфера для проверки контрольных сумм CRC8: один для заголовка (`m_hdrCrc`), другой для всего пакета (`m_pktCrc`), включая первую сумму.
* Опрос (`poll`) реализован с помощью конструкции `switch-case` и перечисления `enum class State : uint8_t`. Это позволяет считывать с физического уровня по одному байту и парсить пакет побайтово, накапливая контрольные суммы. Преимущество такого подхода в том, что при постоянном опросе транспортного, канального и физического уровней объект канального класса «помнит» последнее состояние пакета. Это позволяет начать обработку пакета канального уровня сразу же после получения стартового байта.

В физический уровень пакеты канального уровня передаются в виде потока байт. Полезная нагрузка представляет собой пакет транспортного уровня.

## Транспортный уровень

Этот уровень взаимодействует с канальным. Он предоставляет методы для регистрации функций, выполнения запросов, работы со стримом и получения пакета (`dispatchOnce`).
* В секции `private` реализованы методы обработки всех видов сообщений из `MsgType` (кроме `Error`, который не обрабатывается).
* Класс этого уровня не знает, что его метод `dispatchOnce` вызывается в цикле задачи `AppRxTask` на уровне приложения. Однако он использует семафоры для блокировки кода в момент ожидания ответа на `call` или следующего чанка данных для `stream`. Это позволяет задаче `AppRxTask` продолжать работу, не завершая вызовы `call`/`stream` на уровне приложения мгновенно.
* В методе `stream` используется отдельный семафор для транспортных пакетов стрима. При его получении выставляется флаг и освобождается семафор, чтобы выполнить заданную функцию `StreamCallback`.

## Уровень приложения

С этим уровнем работает пользователь. Интерфейс состоит из методов инициализации физического уровня (и деинициализации), регистрации функций, а также вызова `call` и `stream`. Интерфейс «знает» обо всех звеньях протокола (для физического уровня необходимо написать свою реализацию и передать её при создании объекта класса `App`). Также предусмотрены методы создания пользовательских задач, после чего вызов `vTaskStartScheduler` запустит работу протокола. Задача чтения создается при инициализации через метод `start`.

Цикл чтения (высший приоритет):

```cpp
void App::rxLoop() {
    const uint32_t pollTimeoutMs = 10; 

    for (;;) {
        m_physics.update();

        if (m_physics.isConnected()) {
            if (!m_transport.dispatchOnce(pollTimeoutMs)) {
                vTaskDelay(pdMS_TO_TICKS(1)); // Даем время другим задачам (call() имеет приоритет 1)
            }
        } else {
            m_transport.linkDown();
            vTaskDelay(pdMS_TO_TICKS(100));
        }
    }
}
```

Цикл чтения имеет второй приоритет, тогда как пользовательские задачи `call` и `stream` по умолчанию имеют приоритет 1:

```cpp
bool createClientTask(ClientTaskFunc taskFunc,
                      const char* name = "ClientTask",
                      uint32_t stackBytes = 8192,
                      UBaseType_t priority = 1);

bool createClientStreamTask(ClientTaskFunc taskFunc,
                            const char* name = "ClientStreamTask",
                            uint32_t stackBytes = 8192,
                            UBaseType_t priority = 1);
```

Это сделано для того, чтобы планировщик, запускаемый после настройки приложения программистом, всегда проверял наличие пакетов и выполнял `call` или `stream` только при необходимости. Вызов `vTaskDelay(pdMS_TO_TICKS(1))` дает возможность выполниться задачам с более низким приоритетом пока нет новых целых пакетов. Именно в этих пользовательских задачах подразумевается вызов `call` или `stream`. Вызывать эти методы можно и вне пользовательской задач, но по заданию было необходимо «создать задачу приема сообщений». Это возможно, потому что логика обработки этих методов основана на семафорах и не зависит от задачи, в которой вызывается.

Пользовательские задачи обязательно нужно удалять, поэтому предусмотрен метод `stop`. После его вызова программист может продолжить работу с полученными данными от удаленных функций, «забыв» про физический уровень, деинициализация которого также происходит внутри метода.

Стоит отметить, что для стрима в метод передается функция, которая вызывается в цикле стрима на уровне приложения и принимает указатель на данные и их длину. При этом параметры удаленной функции передаются только один раз в начале стрима:

```cpp
// Отправляем stream-запрос (0x0C)
if (!sendMsg(MsgType::Stream, m_streamSeq, name, args, argsLen)) {
    m_streamBusy = false;
    return CallStatus::Error;
}

for (;;) {
    if (xSemaphoreTake(m_streamSem, pdMS_TO_TICKS(stepTimeoutMs)) != pdTRUE) {
        m_streamStatus = CallStatus::Timeout;
        break;
    }
    if (m_streamDataReady) {
        m_streamDataReady = false;
        if (Chunk) Chunk(m_streamLastBuf, m_streamLastLen);
        continue;
    }
    break;
}
```

`Chunk` — это функция типа `StreamCallback`. При получении пакета стрима она передает последние данные из буфера стрима в пользовательскую функцию для обработки. При этом вызов `app.stream` остается заблокированным до тех пор, пока не придет сообщение `MsgType::Response`. Если флаг `m_streamBusy` поднят и номер пакета `m_streamSeq` совпадает, система сбросит `m_streamStatus`, вернет семафор, и цикл стрима завершится, освободив ресурс для нового вызова стрима (сброс `m_streamBusy`).

## Недостатки

* Транспортный уровень жестко ограничивает количество функций (`MaxFunctions`) и сообщений (`MaxMsg`).
* Пользователь протокола получает результат вызова удаленных процедур в виде массива байт и его длины. Это может быть неудобно при работе со сложными структурами параметров (не просто числа или строки).
* Масштабирование путем добавления новых типов сообщений и их обработки затруднено, так как на транспортном уровне `dispatchOnce` использует конструкцию `if-else`. Добавление новых обработчиков, флагов, типов сообщений и семафоров неудобно. Эта проблема выявилась, когда после реализации `call` нужно было добавить метод `stream`.
* Максимальный размер параметров при вызове удаленных функций на канальном уровне (`kMaxPayload = 256` байт) строго зафиксирован. Это означает, что вызов функций с большими по объему параметрами невозможен.
* Протокол не поддерживает больше одного клиента, так как использует бинарные флаги занятости для методов `call` или `stream`, любой из которых полностью блокирует возможность работы со вторым клиентом (в случае с `stream` блокируется до конца стрима).
* Количество пакетов для стрима зашито в коде (= 5). Невозможно назначить количество желаемых пакетов при отправке стрим запроса.

## Что можно улучшить

* Повысить удобство работы с входными и возвращаемыми параметрами. Например, использовать формат «ключ-значение» и написать для них парсинг/сериализацию.
